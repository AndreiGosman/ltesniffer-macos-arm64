# Loopback validation (no RF)

The port was validated end to end over a ZeroMQ loopback on localhost, with no
SDR and no over-the-air capture. The signal is synthetic, generated by srsRAN.

## Topology

- srsepc (4G core: MME, HSS, SPGW) provides the attach and the bearer.
- srsenb generates the LTE downlink over the ZeroMQ virtual radio.
- A small DL fan-out relays each downlink block to two consumers at once: the
  test UE (srsue) and LTESniffer. srsRAN's ZeroMQ radio is request-reply and
  point to point, so a passive listener alongside a UE needs this fan-out. The
  fan-out pulls the next block from srsenb only after both consumers took the
  current one, which keeps the flow-control lockstep.
- srsue is the test UE. It uses the standard srsRAN test SIM.
- LTESniffer listens passively on the second fan-out port.

## Result

The test UE attached fully: RRC connection setup, security mode, reconfiguration,
a sustained C-RNTI, and an assigned IP. Listening passively, LTESniffer:

- found the cell and decoded the MIB;
- wrote one DCI row per decoded allocation, including the UE's C-RNTI, to the
  DCI CSV, alongside the SI-RNTI broadcast and the RA-RNTI random-access grant;
- produced the control-channel load statistics (decoded locations, used CCEs);
- mapped the C-RNTI to the UE's TMSI, read in the clear from the RRC Connection
  Reconfiguration during a GUTI attach.

Every value cross-checked against the ground truth in the srsRAN logs: the
C-RNTI and the TMSI matched. All identities were the test UE's own.

## What this does not show

The loopback uses a synthetic signal and a test SIM. It validates decode and the
identity mapping, not real-world radio performance.
